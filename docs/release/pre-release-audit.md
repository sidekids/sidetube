## iOS

Welcome suggestions now require parent approval. A narrowly identified legacy autoapproval is migrated to pending; parent approvals and deleted entries are preserved. Root content waits for the safety migration. Player close/background paths release bridges, callbacks and polling tasks; paused JavaScript timers stop. PeerTube uses a nonpersistent WebKit data store. HTTP cache behavior respects protocol freshness. Parent mode relocks on backgrounding.

PIN penalties are bounded and setup verifies that its hash actually persisted before reporting success. Unit tests cover a failing store. Simulator UI evidence verifies bedtime and sleep overlays unlock with a parent PIN on an isolated ad-hoc signed simulator. An earlier unsigned UI run failed to persist the PIN: that run is not counted as a successful security test. Keychain/device recovery behavior remains to test on hardware.

The 2026-09-10 follow-up replaces the fixed child-mode polling interval with deadlines derived from calendar boundaries, remaining daily budget and sleep fade/expiry. Input changes and significant system clock changes reschedule the task; inactive scenes cancel it. The PIN countdown timeline exists only during a foreground lockout. Invalid enabled bedtime settings fail closed instead of disabling protection. Nine scheduling tests cover idle/no-rule behavior, warnings, weekend offsets, exception expiry, midnight, bounded fade and DST transitions. Real-device scheduling delays and enforcement still need measurement.

Watch-time write failures are no longer swallowed with `try?`. Failed saves stop the player, retain the uncommitted record in memory and block further player loads within the coordinator lifetime; the child sees a storage-error overlay rather than a misleading time-limit/network message. Eight injected-failure transition cases and a coordinator close/reopen test exercise the shared failure path. This in-memory latch alone does not provide durable recovery or certify SwiftData read-error behavior; see [write-failure scope and remaining gates](ios-watch-time-failures.md).

Playback accounting now uses monotonic uptime independently of calendar timestamps, excludes buffering/unstarted/cued states and reconciles missing state callbacks from the existing position signal. Short-session rounding is conservative. API failure and foreign-video rejection no longer discard the requested video's elapsed time; late playing callbacks cannot revive an ended/failed model. Clock-change, state-transition, rounding and late-callback tests cover this correction.

Calendar-day splitting (2026-09-13): a continuous playing stretch crossing midnight previously booked its entire watched time to whichever day the record happened to be flushed on, silently debiting the new day's fresh daily allowance for time actually watched the day before. `PlayerModel` now captures a wall-clock anchor once per playing stretch and, when the stretch is paused or closed, splits the accumulated seconds at each calendar-day boundary it crossed into one `WatchHistoryEntry` per day — an earlier, already-completed day at its own start-of-day timestamp, the most recent (or only) day at the actual flush time exactly as before. This changes only which day(s) a session's watched time is attributed to; it deliberately does **not** change when or whether a session may keep playing past midnight - the existing single pre-midnight budget check for the whole session is untouched, so a session already permitted to run past midnight still does. A failure partway through a multi-day flush leaves every not-yet-recorded day's seconds uncommitted, matching the existing single-day failure behavior. Four new tests cover the midnight split, the live remaining-time estimate mid-crossing, and failure retention; verified on the iOS 26.5 simulator only (not re-run on 26.4). 186 tests total after this change (was 183).

Following the Android admission-marker policy, iOS persists a `PlaybackAdmission` marker (profile ID, session token, start time) before creating a player and removes it only after a clean close has durably flushed watch time. An interrupted session requires parent-PIN recovery; acknowledgement preserves recorded history and does not estimate missing time. Repository/coordinator tests cover profile isolation, duplicate admission, stale tokens, clean close, recovery and storage errors. A disk-backed test verifies marker and acknowledgement persistence across separate container lifetimes; both deletion paths preserve unrelated pending parent edits. **Migration evidence corrected and extended:** the original test only proved current-schema reopening. A new test freezes all six pre-change model declarations from `7898667`, verifies absence of the marker entity, creates synthetic data and migrates the resulting disk store to the seven-entity production schema. Profiles, approval states and history survive under iOS 26.5. Older-OS store upgrades, signed-app updates and real force-stop/PIN-UI tests remain required; see [interrupted-session recovery](ios-watch-time-failures.md).

Both platform repositories now fail closed on invalid/overflowing daily-limit values and corrupt negative history. iOS uses checked summation; Android reads the SQLite sum as 64-bit and saturates safely rather than truncating it into extra allowance. Existing records are preserved, not silently repaired or deleted. Boundary tests pass on both platforms.

## Android

The current client is a native Kotlin/Compose replacement, not the historical GPL package. Missing packaged content/test resources caused ten baseline failures and are fixed. SDK 36 / AGP 8.9.3 builds pass; shared product version remains 0.1.0. R8 annotation inputs are compile-only. Lifecycle-aware UI collection, cancelled profile collectors, playback-profile accounting and active-player-scoped WebView ownership address concrete resource/state defects. Cached and fresh trusted-channel browsing now honor prior decisions and risk policy.

The top-level player origin comparison and JavaScript arguments are validated. Subframe navigation was previously unchecked entirely (`shouldOverrideUrlLoading` returned `false`/allow for any non-main-frame request); a link inside the embedded YouTube iframe (the logo, an end-screen suggestion, an ad redirect) could take that surface to the full youtube.com site — search, sign-in, ads, related videos — without leaving the app. A new pure `PlayerNavigationPolicy` (unit-tested, no Robolectric) now restricts subframe navigation to the YouTube IFrame API's own `/embed/…` document on a fixed host allowlist; a host-only check would not have been sufficient, since `youtube.com/watch` is still `youtube.com`. This does **not** close cookie risks, native controls (the visible YouTube logo/branding) are unchanged, and real click-through behavior of the embedded player on a device is unverified.

Cookie follow-up: player cookies are now scoped to a session. The embed previously loaded from `www.youtube.com` while iOS used `www.youtube-nocookie.com`; Android now uses the same privacy-enhanced host, which `PlayerNavigationPolicy` already permitted. `CookieManager` is process-wide and disk-backed, so a new pure `PlayerCookiePolicy` (unit-tested, no Robolectric) clears the store when a session begins — an aborted predecessor session (renderer death, force-stop) never reaches its end — and blocks, clears and flushes it on teardown. Three ordering tests cover this. This closes cookie persistence across sessions; it does **not** close third-party cookies. The earlier observation that playback fails without them was made on the `www.youtube.com` embed, so whether they remain necessary after the host change requires device measurement rather than an assumption here. The host change itself is device-unverified and touches the Android-only error-153 referer workaround (`widget_referrer`, `fixReferrer`) that iOS does not carry; a device must confirm that playback still starts, including on an older WebView build. `PLAYER_SECURITY.md` previously claimed Android used no third-party cookies in the child player; that claim was inaccurate and has been corrected.

Separately, the embedded IFrame could load a video the app never requested (an end-screen card or pause-screen suggestion triggered by YouTube's own script, not a URL navigation — outside what `PlayerNavigationPolicy` above can see) and nothing detected or stopped it. `player.html` now tracks the last requested video ID and compares it against `getVideoData()` on every playing/buffering state and time tick, mirroring iOS's `guardForeignVideo`; a mismatch stops playback and reports it to `PlaybackModel.onForeignVideo`, which books only the originally requested video's already-accumulated time (never under the foreign ID) and ends the session regardless of the autoplay setting. Three new `PlaybackModelTest` cases cover this. The former startup warmup workaround was removed from the active path; a 2026-09-13 morning session confirmed ordinary playback still renders and progresses on a physical SidePhone without it. A later same-day session could not reproduce that: repeated attempts stalled at "loading" regardless of whether the nocookie-host change was present, reverted, or the pre-cookie-change commit was installed outright - ruling out that change as the cause but leaving the stall itself, and therefore the nocookie-host change's actual functional status, unresolved; see [device verification](android-device-verification.md) for the isolation steps. No Android instrumented/device test suite was run; the subframe-navigation and foreign-video guards' actual click-through behavior is still unverified on hardware.

Follow-up: daily limits now check persisted remaining time before playback and stop exhausted sessions using a cancellable deadline only while playing. Queue/autoplay changes preserve the session budget. Rapid reopening waits for queued history writes; storage errors fail closed within the ViewModel lifetime. Viewing uses a monotonic clock; buffering/cued states stop accounting, and player errors record the correct video before advancing. Partial seconds are rounded up when persisted to prevent repeated short sessions discarding all watch time. Eleven additional core tests cover these boundaries.

This does not close the time-control release gate: ViewModel scheduling, background/foreground transitions and real-player shutdown need integration/device tests.

Sleep-timer follow-up: the previously missing sleep mode exists. Parents set a duration in the PIN-gated area and return to child mode; a pure `SleepTimerPolicy` derives everything from the end instant rather than an "expired" flag, so a clock moved backwards lets the timer run on instead of staying expired. The ViewModel arms one deadline until the fade window and then ticks once per second for the final minute only — the single recurring wake-up in the app, deliberately bounded — lowering volume through a new `SetVolume` command. On expiry the player closes and the timer stays expired, so the child cannot simply start the next video; only a parent clears it. Bedtime and sleep are now asked through one `enforceTimeRules` so no entry path checks only half the rules. Six policy tests and five ViewModel tests against a settable clock cover expiry, the fade ramp, the restart block, parent cancellation and a backwards clock jump. This is not device-validated: real background/foreground transitions, doze behaviour and audible fade on hardware remain untested, and the timer does not survive process death.

Calendar-day splitting (2026-09-13), mirroring the iOS fix above: `PlaybackModel` now records a wall-clock anchor alongside its existing monotonic one when a playing stretch starts, and splits accumulated milliseconds at any calendar-day boundary crossed when the stretch closes. `Command.Record` gained an optional `at` field — `null` for the current/most recent day (unchanged: `KidViewModel` still stamps it with the real time when processing the command), an explicit start-of-day timestamp for any earlier, already-completed day. This changes only which day's watch history the seconds land in; the existing single pre-midnight budget deadline for the whole session is unchanged, so a session already permitted to keep playing past midnight still does. Day-boundary computation uses the same device time zone as the existing daily-limit query (`WatchTimeRepository.dayBounds`). Four new `PlaybackModelTest` cases cover the crossing split, the live watched-seconds estimate mid-crossing, and that both days arrive as separate commands so a persistence failure on one cannot silently discard the other.

Kid-mode profile switching (2026-09-13): the child screen always showed `profiles.firstOrNull()`, with no way to reach a second child's profile at all - carried in [feature-parity.md](feature-parity.md) as a missing-selection gap. `KidViewModel` now tracks the selected profile id separately from the profile list, resolving it on every list emission (selection, then the persisted last-used id, then the first profile, in that order) so an unrelated whitelist/source refresh cannot silently switch which child is active. `selectProfile()` persists the choice via a new `ProfilePreferenceStore`/`SharedPreferences` (a plain preference, not `PinStore` - it holds no secret). The header title's long-press opens a switcher when more than one profile exists; a short tap still goes home, so this does not change single-profile behavior. Three ViewModel tests cover switching, that an unrelated whitelist emission does not revert the selection, and that the selection survives a fresh `KidViewModel` instance (simulating relaunch) via the persisted id. Not device-tested: the long-press gesture's discoverability and behavior on hardware.

Following the user's approval of parent-PIN recovery, Android schema 2 persists an admission marker before playback. An interrupted session blocks fresh playback until explicit confirmation in the PIN-gated parent area; successful close removes the marker only after queued history writes complete. Acknowledgement preserves recorded time and does not guess missing time. Token-scoped completion prevents stale jobs clearing newer sessions. File-backed reopen, profile-isolation and schema-1→2 migration tests pass without deleting historical records. **2026-09-13: full physical-device confirmation, in two passes.** A real `am force-stop` mid-playback on a SidePhone left the marker in place, and every subsequent playback attempt for that profile was correctly refused with the expected message. The parent-side completion was reached later the same day, after an owner-authorized PIN reset (the existing PIN was unknown; only `PinStore`'s own preference file was deleted, not profile/history data) - entering the new PIN, confirming "Unterbrochene Wiedergabe prüfen", and receiving "Unterbrochene Wiedergabe freigegeben. Gespeicherte Sehzeit bleibt erhalten." A separate marker from this same testing was also observed surviving a full `adb install -r` update, not just a relaunch. See [device verification](android-device-verification.md) for both passes, and for an unrelated, unresolved playback-stall finding from the same session. iOS now has an equivalent marker (see [write-failure scope and remaining gates](ios-watch-time-failures.md)), still without device/UI testing on that platform. See [recovery semantics and device gates](android-time-control.md).

Quiet-hours follow-up: playback is checked before start, after asynchronous history reads, on player events and before load/resume commands. A cancellable boundary deadline closes active/paused/loading players when the rule becomes active. Friday/Saturday offsets, exclusive end time and stored parent exceptions follow the existing iOS wall-clock semantics. Invalid enabled settings fail closed. DST transitions, repeated hours and clock/time-zone changes are explicitly handled. Nine new policy tests pass. [Time-control device gates](android-time-control.md) remain open.

Quiet-hours parity follow-up: the evaluator returns iOS's three states instead of a boolean, so the child is warned fifteen and five minutes before the start rather than being cut off mid-video; the warning thresholds are now themselves scheduling boundaries, without which the warning could never arrive. `bedtimeSkipUntil` existed in the schema and was honoured by the policy but no surface could set it — dead protection. Parents can now suspend a running quiet hour from the PIN-gated profile list, bounded to the end of that window rather than a freely chosen duration, so an exception cannot become an off switch. Corrupt settings still fail closed but no longer yield an exception end: a stored end of 99999 minutes would otherwise have granted an exception lasting weeks. Four policy tests and two ViewModel tests against a settable clock cover the warnings, the exception and that window end. The full-screen child overlay is still missing — Android shows a dismissible hint where iOS blocks the screen — and none of this is device-validated.

## Remaining Risks

1. **BLOCKER — child safety (device evidence only):** every Android protection the audit asked for is implemented and unit-tested (lock, navigation and foreign-video guards, session-scoped cookies without third-party cookies, time rules); what is missing is end-to-end validation on the physical SidePhone with its old WebView, including the 2026-09-13 playback stall that was never explained. See the [checklist](device-checklist.md).
2. **BLOCKER — privacy/provider model:** approve target audience, third-party behavior and accurate public disclosures; close cookie/navigation risks without violating provider requirements.
3. **BLOCKER — provenance/rights:** owner must substantiate the Android replacement and approve distributable assets/content and author metadata.
4. **BLOCKER — device evidence:** complete energy, accessibility, network, player teardown and failure/recovery matrices on supported hardware.
5. **BLOCKER — migration/release:** extend the passing frozen-schema iOS migration test to older-OS stores and signed-app upgrades, decide other existing-user data migrations, decide which remaining parity gaps block the first version (localization is done), validate signed artifacts and obtain separate publication authority.
6. **WARNING — supply chain:** runtime POM/OSV review does not cover every tool/test component; hosted CI and repeatable clean-machine builds remain unverified.

## Recommendation

Keep the developer-based audit branch private and do not tag a release candidate yet. Preserve the functioning native implementation and current backups. The Android protective behavior is in place; next collect physical-device evidence with the [checklist](device-checklist.md), decide the child-directed provider model and resolve provenance/asset rights. Only after all BLOCKER entries are closed should the public canonical-history migration and signed release-candidate process proceed, with explicit publication approval.
