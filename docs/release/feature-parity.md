# Feature parity — replacement Android baseline

Static code evidence, not a claim of end-to-end device validation. This supersedes historical `CROSS_PLATFORM_PARITY.md` assertions about the former Android implementation.

| Capability | iOS | Current Android | Assessment |
|---|---|---|---|
| Child home/navigation | Tabs, cards, wheel sheet | One list with section headers (Zuletzt geschaut · Kanäle · Sendungen · Videos · „Alle Videos“), library screen with a Kanäle/Videos/Sendungen switcher (one focus stop, Select cycles), back stack that restores the previous selection, hardware-key focus, search via key and magnifier button | Native differences intentional; no „Weiterschauen“ progress because Android stores no playback position; device check pending |
| Profiles | Multiple profiles and child selection; profile editor | Parent CRUD; child selection now present (long-press the header title, persisted across restarts); profile editor (2026-10-02, pencil per profile) with name, age band, content switches, Shorts, autoplay, quiet hours incl. Fri/Sat offset and daily limit 5–300 min, iOS ranges and labels | Device UX/gesture-discoverability unverified; iOS sleep-playlist field omitted because Android does not read it |
| Whitelist | Videos/channels/playlists; since 2026-10-02 approved playlists load from the keyless playlist feed (`RSSFeedClient.playlistVideos`, same parser as the channel feed, cached as `playlist:<id>`), the Data API only pages further when a key exists; videos filtered by `ContentPolicy.canPlayFromPlaylist`, also at the player boundary (`SafeRecommendationService.allowed`) | URL resolution and stored entries; approved playlists open a list of their videos from the keyless playlist feed (`PlaylistFeedSource`, cached as `playlist:<id>`), filtered by `ContentPolicy.canPlayFromPlaylist` | Same rule on both (per-video decision wins, risk screen, no shorts/live incl. the feed's `/shorts/` link and `views="0"`, playlist age/category, blocked channel or playlist source; since 2026-10-03 videos from channels with „Nur einzeln geprüfte Videos“ or with unknown channel ID need their own approval, sources are matched by channel ID only – [ADR 0002](../adr/0002-playlist-videos-und-einzelpruefung.md)); without a key both show only the first 15 entries, with a key iOS pages through the Data API; iOS additionally treats the profile's sleep playlist as parent-approved |
| Parent approval queue | Present: approve/reject/later, optional maximum age, decision history | Present via ReviewScreens/CurationRepository; since 2026-10-02 also „Später“, optional „Höchstalter“ and the per-profile „Verlauf“ in the decision dialog | Defaults pending; test policy edge cases on both; news-status picker still iOS-only |
| Children's wishes ([ADR 0001](../adr/0001-wuensche-von-kindern.md)) | Present since 2026-10-02: topic wish from search (first when nothing is found), „Mehr davon“ in the player toolbar and on the end card, „Neu bei deinen Kanälen“ on Home (locked tiles from the keyless channel feed of whitelisted channels with „Vertrauenswürdige Reihe“: ≤ 6 per channel, ≤ 60 days, no Shorts/live/premieres, title risk filter incl. topic hints, known or rejected videos excluded, blocked/parent-only sources never), „Meine Wünsche“ (status, parent reply, open approved content), wishes first in the review queue with the ADR actions, every wish/decision as `ReviewEvent`; 3 per profile and day, pending duplicates not recreated; optional parent notification (ADR 0005, see below) | Since 2026-10-02: topic wish from the wheel search (row „Wunsch an die Eltern“, free letter wheel A–Z/Ä/Ö/Ü/ß), „Mehr davon“ on the end card and in a player menu (outer top-right key), „Neu bei deinen Kanälen“ on Home (≤ 6 newest per channel at trust `trustedSeries`, ≤ 60 days, no Shorts/live, risk filter on titles, nothing with a prior decision, never blocked sources; locked, only wishable), „Meine Wünsche“ with status and parent reply; parent review list shows wishes first with the ADR actions and an optional reply; Room table `wishes` (schema 3), events in the review history; 3 per profile and day, no duplicates; optional parent notification (ADR 0005) | Unit-tested (`WishTests.swift`); simulator scenes T14–T17 plus `WuenscheUITests` (approved wish opens the video, daily limit disables „Wünschen“); live/premiere detection in the feed is heuristic (title terms, `views="0"`); wheel/remote selection does not reach the locked tiles; Android: Same rules as the ADR; emulator walk-through 2026-10-02 (all three ways and the parent decision by keys/touch); duplicates as on iOS (same key while open or under discussion); device check on a real SidePhone pending |
| Parent notification of new wishes ([ADR 0005](../adr/0005-eltern-ueber-wuensche-benachrichtigen.md)) | Since 2026-10-05: ⋯ → „Eltern benachrichtigen“ – setup code by QR scan (AVFoundation) or paste (`PasteButton`), „Test senden“, „Neu einrichten“, „Entfernen“; setup in the Keychain; each new wish posts „@<parents> SideTube: neuer Wunsch (N offen)“ to a Nextcloud Talk bot in the background (`WishFeedback.submit` → `WishRepository.notifyParents`) | Since 2026-10-05: „Weitere“ → „Eltern benachrichtigen“ with the same texts – QR scan (CameraX + ZXing core, no Google services) or paste from the clipboard; setup in its own EncryptedSharedPreferences file; sending from an app-wide background scope (`AppContainer.meldeNeuenWunsch`) | Same rules and the same signature test vectors on both; real send from both clients against a Nextcloud 32 / Talk 22 server answered 201; on 2026-10-05 a real SidePhone SP-01 scanned the setup code from a screen and its „Test senden“ arrived in the parents' regular Nextcloud app on an iPhone; QR scan on a real iPhone and wheel-only operation on the SidePhone pending |
| Starter packs | Shared content and pending welcome suggestions | Shared libraries, no equivalent welcome flow | Packaging fixed; UI behavior differs |
| Source trust | Registry, parent changes, trusted browsing | Registry, parent changes, browsing; German level titles as on iOS, reached via ⋯ → „Quellen & Sicherheitsstufen“ | Cached entries were shown before trust check on Android; ordering corrected |
| Risk/age/category checks | Policy and RiskScreen, disabled categories | Policy and RiskScreen | Trusted browsing and feature defaults need fuller equivalence tests |
| Search | Approved/cache search, parent Data API options | Local search in approved titles and channel names; on the Sidephone a letter wheel that offers only letters leading to a match (T9 kept for digit keys) | No equivalent provider search; cached channel videos are not searched |
| Favorites | No distinct verified favorites flow | No distinct verified favorites flow | Do not advertise as present |
| YouTube playback | Custom controls, captions, seek, fullscreen, guarded foreign ID | WebView controls plus native buttons, Activity-hosted surface; subframe navigation and foreign-video ID now guarded like iOS | Native YouTube controls (incl. logo) stay visible unlike iOS's custom controls; no device click-through verification; BLOCKER |
| End state / next | Done UI, controlled suggestions | End card „Fertig 🎉“ with „Nochmal“ and „Zurück zu den Videos“ (Up/Down select, Select confirms), no suggestions, no autoplay | No „Als Nächstes“ suggestions on Android; device check pending |
| Autoplay | Parent option, default off | Stored option consumed by PlaybackModel | Default matches; real provider behavior unverified |
| Time limits | Live enforcement/overlays; in-memory write-failure latch; durable interrupted-session marker with parent recovery; watch-history now split per calendar day crossed | Persisted budget checked before start; monotonic deadline and durable interrupted-session marker with parent recovery; watch-history now split per calendar day crossed | Since 2026-10-08 Android shows the PIN-locked „Die Zeit ist um“ lock (before start and on exhaustion), lifting at midnight or a raised limit; device/integration tests remain BLOCKER; a session already running past midnight still keeps its pre-midnight budget for the whole session on both platforms (deliberate, unchanged) |
| Quiet hours | Blocking overlay, warnings, parent exception UI | Since 2026-10-08 ([ADR 0007](../adr/0007-android-vollbild-sperre.md)): PIN-locked full-screen lock (`KidSperreView`) also while browsing, two warnings before the start, parent exception until the window ends from the lock or the parent area; lifts itself at the window end | Code-equivalent; device verification remains BLOCKER |
| Sleep timer | Present | Parent-set duration, bounded volume fade, expiry closes the player and shows the PIN-locked lock (since 2026-10-08) | ViewModel tests pass, device verification remains BLOCKER |
| Watch history/statistics | Persistence and UI (`WatchStatsView`: period, total, per-day bars, most watched) | Since 2026-10-09 the same: „Nutzung“ per profile (bar-chart icon in the profile list), `WatchStats` in core mirrors `WatchStatsCalculator`, 4 unit tests, seen on the emulator | Equivalent; iOS counts plays the same way |
| PeerTube | Allowlist-based API/player | No current runtime implementation | Missing; do not restore old unrelated code |
| Export/import/migration | Starter imports; no verified general roundtrip | Starter imports; no verified legacy migration | Existing installations need migration decision |
| Parent PIN | PBKDF2/Keychain, persistent lockout, change PIN | PBKDF2/EncryptedSharedPreferences, lockout; change PIN via ⋯ → „PIN ändern“ (current PIN checked against the same lockout) | Capped penalties and corrupt-data tests; main-thread hashing remains to measure |
| Background | Player teardown and parent relock added | Player teardown and parent relock added | Device verification pending |
| Cookies | Nonpersistent players | Session-scoped store cleared at start and teardown, privacy-enhanced host; third-party cookies still accepted | Partial: remaining third-party acceptance and device verification stay Privacy BLOCKER |
| Caching | SwiftData channel cache, memory HTTP cache, AsyncImage | Room channel cache, simple HTTP client | Different cache freshness/cancellation policies |
| Offline | Local curated data/cache; streaming unavailable | Local data/cache; streaming unavailable | Error/slow-network/geo restriction device matrix pending |
| Deep links / external shares | Recommendation links, parent-gated save/open | No comparable deep-link workflow | Optional platform difference; initial iOS lookup precedes PIN |
| Accessibility | Labels, Dynamic Type usage, mixed motion handling | Native text/content descriptions and hardware focus | VoiceOver/TalkBack and large-font gates unrun |
| Localization | Since 2026-10-09: string catalog (de source, en) with 575 keys – SwiftUI literals plus `String(localized:)` for domain titles, kid-mode model texts, feedback and overlay texts; data, logs and fixtures stay German | Since 2026-10-09 ([ADR 0008](../adr/0008-android-lokalisierung.md)): all UI strings in `strings.xml` (German source, ~400 entries, plurals), ViewModels resolve through `Texte`; persisted data (actor, notes, wish titles in history) stays German by design | English on both: iOS catalog (checked on the simulator with `-AppleLanguages (en)`), Android `values-en/strings.xml` (checked on the SP-01 emulator with the system locale set to en-US) |
| Dark mode | Child mode forces dark; parent native behavior | Compose theme | Native differences; contrast measurement pending |

No missing feature was invented merely to expand scope. Completing the absent protective behavior and agreeing which other parity gaps are required for the first public version remain necessary before a release candidate can be approved.
